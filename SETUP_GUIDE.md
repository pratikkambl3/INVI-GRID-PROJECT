# AWS IAM Identity Center (SSO) & EKS Access Policies Setup Runbook

Step-by-step operational and deployment runbook for provisioning a **100% Strictly Private Amazon EKS Cluster** using **AWS IAM Identity Center (formerly AWS SSO)** and **EKS Access Entries with Access Policies**.

---

## 1. Architecture & 3-Group Permission Matrix

```
  Identity Provider (SSO)       IAM SSO Role              EKS Access Entry         EKS Access Policy         Authorized Scope
 ───────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────
  Group: EKS-Admins         ──▶ AWSReservedSSO_EKS-Admin     ──▶ Type: STANDARD ──▶ AmazonEKSClusterAdminPolicy ──▶ Cluster-wide (All Namespaces)
  Group: EKS-ReadOnly       ──▶ AWSReservedSSO_EKS-ReadOnly  ──▶ Type: STANDARD ──▶ AmazonEKSViewPolicy         ──▶ Cluster-wide (Read-Only)
  Group: EKS-Developers     ──▶ AWSReservedSSO_EKS-Developer ──▶ Type: STANDARD ──▶ AmazonEKSViewPolicy         ──▶ Namespace 'dev' ONLY (Read-Only)
```

### Exact Group Boundary Rules:
1. **Admin (`EKS-Admin`)**:
   - Cluster-wide administrative control across all namespaces (`dev`, `qa`, `production`, `kube-system`).
2. **ReadOnly (`EKS-ReadOnly`)**:
   - Cluster-wide read-only view across all namespaces. Can inspect pods, services, and workloads in any namespace, but **cannot** create, modify, patch, or delete resources.
3. **Developer (`EKS-Developer`)**:
   - **Only has access to the `dev` namespace, and that too ONLY read access**.
   - Can view pods, services, deployments, and logs in `dev`.
   - **Denied** from creating or modifying any resource in `dev`.
   - **Strictly denied (403 Forbidden)** from accessing `qa`, `production`, or any other namespace.

## 2. Step 1: Configure AWS IAM Identity Center (SSO)

Follow these steps in the AWS Console (or AWS CLI) if IAM Identity Center is enabled in your AWS account or AWS Organization:

### A. Create Groups & Users in IAM Identity Center
1. Navigate to **IAM Identity Center** in the AWS Console.
2. Go to **Groups** and create 3 groups:
   - `EKS-Admins`
   - `EKS-ReadOnly`
   - `EKS-Developers`
3. Go to **Users** and assign users to their respective groups (e.g. `dev-user@company.com` added to `EKS-Developers`).

### B. Create Permission Sets
In IAM Identity Center, go to **Permission sets** and create 3 permission sets:
1. **`EKS-Admin`**:
   - Session duration: 8 hours
   - Inline policy (minimum permissions to describe cluster and list clusters):
     ```json
     {
       "Version": "2012-10-17",
       "Statement": [{
         "Effect": "Allow",
         "Action": ["eks:DescribeCluster", "eks:ListClusters"],
         "Resource": "*"
       }]
     }
     ```
2. **`EKS-ReadOnly`**:
   - Attach the same inline `eks:DescribeCluster` and `eks:ListClusters` policy.
3. **`EKS-Developer`**:
   - Attach the same inline `eks:DescribeCluster` and `eks:ListClusters` policy.

### C. Assign Permission Sets to AWS Account
1. In IAM Identity Center, go to **AWS accounts**.
2. Select your target account and click **Assign users or groups**.
3. Map:
   - Group `EKS-Admins` $\rightarrow$ Permission set `EKS-Admin`
   - Group `EKS-ReadOnly` $\rightarrow$ Permission set `EKS-ReadOnly`
   - Group `EKS-Developers` $\rightarrow$ Permission set `EKS-Developer`

> [!NOTE]
> AWS automatically creates an IAM Role in your account for each assigned permission set, starting with `AWSReservedSSO_`.

## 3. Step 2: Retrieve SSO Role ARNs

From your administrator AWS CLI session, find the IAM roles generated by Identity Center:

```bash
# Query SSO roles generated by Identity Center:
aws iam list-roles \
  --query "Roles[?starts_with(RoleName, 'AWSReservedSSO_')].[RoleName,Arn]" \
  --output table
```

Example output:
```
--------------------------------------------------------------------------------------------------------------------------------------------
|                                                                 ListRoles                                                                |
+------------------------------------------------+-----------------------------------------------------------------------------------------+
|  AWSReservedSSO_EKS-Admin_1234567890abcdef     |  arn:aws:iam::123456789012:role/aws-reserved/sso.amazonaws.com/AWSReservedSSO_EKS-Admin_...  |
|  AWSReservedSSO_EKS-ReadOnly_1234567890abcdef  |  arn:aws:iam::123456789012:role/aws-reserved/sso.amazonaws.com/AWSReservedSSO_EKS-ReadOnly_...  |

```

## 4. Step 3: Provision Infrastructure & EKS Access with Terraform

### A. Configure `terraform.tfvars`
Open `e:\INVI-GRID Project\terraform\terraform.tfvars` and set the SSO role ARNs:

```hcl
aws_region   = "ap-south-1"
cluster_name = "invigrid-eks"

# Set the SSO Role ARNs retrieved from Step 2:
sso_admin_role_arn     = "<SSO_ADMIN_ROLE_ARN>"
sso_readonly_role_arn  = "<SSO_READONLY_ROLE_ARN>"
sso_developer_role_arn = "<SSO_DEVELOPER_ROLE_ARN>"
```

*(If you haven't set up SSO yet, you can leave them empty; Terraform will provision the 3 groups using IAM user principals as defaults, and you can add the SSO ARNs anytime.)*

### B. Apply Terraform
```powershell
cd "e:\INVI-GRID Project\terraform"
terraform init
terraform apply -auto-approve
```

### What Terraform Provisions:
1. **100% Private EKS 1.30 Cluster** with `authentication_mode = "API_AND_CONFIG_MAP"`.
2. **Bastion Jumpbox** with `kubectl`, Helm, and Kubernetes manifests pre-installed.
3. **EKS Access Entries & EKS Access Policies**:
   - `admin`: Associated with `AmazonEKSClusterAdminPolicy` (cluster scope).
   - `readonly`: Associated with `AmazonEKSViewPolicy` (cluster scope).
   - `developer`: Associated with `AmazonEKSViewPolicy` (namespace scope: `dev` ONLY).

## 5. Step 4: Apply Kubernetes Manifests via Bastion

Connect to the Bastion jumpbox to apply namespaces and sample workloads:

```powershell
$BASTION_IP = (terraform output -raw bastion_public_ip)
ssh -i "bastion-key.pem" ec2-user@$BASTION_IP
```

Inside the Bastion session:
```bash
# Update kubeconfig
aws eks update-kubeconfig --region ap-south-1 --name invigrid-eks

# Apply namespaces and sample workloads
cd /home/ec2-user/k8s
./apply-all.sh
```

## 6. Step 5: Configure `aws configure sso` on Developer Workstation

On the developer's laptop or workstation (PowerShell, macOS, or WSL):

### 1. Run `aws configure sso`
```bash
aws configure sso
```

Enter your IAM Identity Center parameters:
```
SSO session name: my-company
SSO start URL: https://my-sso-portal.awsapps.com/start
SSO region: ap-south-1
SSO registration scopes: sso:account:access
```

1. The default browser opens automatically.
2. Enter your company login credentials.
3. Click **Allow access** to authorize the AWS CLI.
4. Select your **AWS Account**.
5. Select your Permission Set:
   - For Developer: Choose `EKS-Developer`
   - For ReadOnly: Choose `EKS-ReadOnly`
   - For Admin: Choose `EKS-Admin`
6. Specify CLI profile name: `eks-developer` (or `eks-readonly` / `eks-admin`).

### 2. Login & Authenticate
```bash
aws sso login --profile eks-developer
```

### 3. Generate Kubeconfig for Private Cluster Access
```bash
aws eks update-kubeconfig \
  --name invigrid-eks \
  --region ap-south-1 \
  --profile eks-developer
```

## 7. Step 6: Connect to the Private EKS Cluster via SSH Tunnel

Because the EKS API server is 100% private (`endpoint_public_access = false`), forward traffic through the Bastion jumpbox:

### A. Open SSH Tunnel in a Background Terminal
```powershell
$BASTION_IP = (terraform output -raw bastion_public_ip)
$EKS_ENDPOINT = (terraform output -raw eks_cluster_endpoint).Replace("https://", "")

ssh -i "bastion-key.pem" -N -L 6443:${EKS_ENDPOINT}:443 ec2-user@${BASTION_IP}
```

### B. Point Local Kubeconfig to localhost:6443
```powershell
kubectl config set-cluster (kubectl config view -o jsonpath='{.clusters[0].name}') `
  --server=https://localhost:6443 `
  --insecure-skip-tls-verify=true
```

## 8. Step 7: Verification & RBAC Testing Runbook

Execute these exact verification commands to prove the 3-group boundaries.

---

### Test 1: Developer Access (`EKS-Developer` / `eks-developer`)
> **Constraint**: Can ONLY access namespace `dev`, and that too ONLY read access.

```bash
# Verify identity
aws sts get-caller-identity --profile eks-developer

# 1. ALLOWED: View pods in 'dev' namespace
kubectl get pods -n dev
# -> Status: SUCCESS (Lists pods)

# 2. ALLOWED: View logs in 'dev' namespace
kubectl logs -l app=dev-sample-app -n dev
# -> Status: SUCCESS

# 3. DENIED: Create a resource in 'dev' (Read-Only restriction!)
kubectl create deployment test-app --image=nginx -n dev
# -> Expected Output:
# Error from server (Forbidden): deployments.apps is forbidden: User cannot create resource "deployments" in API group "apps" in the namespace "dev"

# 4. DENIED: Access 'qa' namespace
kubectl get pods -n qa
# -> Expected Output:
# Error from server (Forbidden): pods is forbidden: User cannot list resource "pods" in API group "" in the namespace "qa"

# 5. DENIED: Access 'production' namespace
kubectl get pods -n production
# -> Expected Output:
# Error from server (Forbidden): pods is forbidden: User cannot list resource "pods" in API group "" in the namespace "production"
```

---

### Test 2: ReadOnly Access (`EKS-ReadOnly` / `eks-readonly`)
> **Constraint**: Can view resources across ALL namespaces, but CANNOT create or modify anything.

```bash
# 1. ALLOWED: View pods in 'dev'
kubectl get pods -n dev
# -> Status: SUCCESS

# 2. ALLOWED: View pods in 'qa'
kubectl get pods -n qa
# -> Status: SUCCESS

# 3. ALLOWED: View pods in 'production'
kubectl get pods -n production
# -> Status: SUCCESS

# 4. DENIED: Create deployment in 'dev'
kubectl create deployment test-app --image=nginx -n dev
# -> Expected Output: Forbidden

# 5. DENIED: Create deployment in 'production'
kubectl create deployment test-app --image=nginx -n production
# -> Expected Output: Forbidden
```

---

### Test 3: Admin Access (`EKS-Admin` / `eks-admin`)
> **Constraint**: Full cluster administration across all namespaces.

```bash
# 1. ALLOWED: List all pods across all namespaces
kubectl get pods -A
# -> Status: SUCCESS

# 2. ALLOWED: Inspect nodes
kubectl get nodes
# -> Status: SUCCESS

# 3. ALLOWED: Create / manage workloads in production
kubectl create deployment admin-test --image=nginx -n production
kubectl delete deployment admin-test -n production
# -> Status: SUCCESS
```
